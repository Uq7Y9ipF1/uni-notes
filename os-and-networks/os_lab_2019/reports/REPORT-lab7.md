## Как реализовано (задание 1)

Во всех четырёх файлах `#define SERV_PORT` / `#define BUFSIZE` заменены на параметры командной строки с валидацией (буферы переведены со статических массивов на `malloc` заданного размера):

| Программа | Было | Стало |
|---|---|---|
| tcpserver | порт зашит 10050, BUFSIZE 100 | `./tcpserver <port> [bufsize]` |
| tcpclient | ip/port уже argv, BUFSIZE 100 | `./tcpclient <ip> <port> [bufsize]` |
| udpserver | порт зашит 20001, BUFSIZE 1024 | `./udpserver <port> [bufsize]` |
| udpclient | ip argv[1], порт зашит | `./udpclient <ip> <port> [bufsize]` |

Создан `lab7/src/makefile` с целями `all/tcpserver/tcpclient/udpserver/udpclient/clean`. Сборка: `make` — все четыре бинарника собираются (осталось одно безвредное предупреждение про неиспользуемую переменную `cliaddr`, унаследованную из исходного кода).

**Фактические прогоны:**

## Задание 2 — ответы на вопросы

**1. Что делают оба приложения?**
Это пары «эхо-сервер + интерактивный клиент». TCP-вариант: сервер принимает соединение и печатает в stdout всё, что прислал клиент (клиент читает stdin и пересылает). UDP-вариант: сервер принимает датаграмму `recvfrom` и **отправляет её обратно** тому же адресату (`sendto`), клиент печатает `REPLY FROM SERVER=`.

**2. tcpclient → незапущенному TCP-серверу?**
Хэндшейк SYN не на кого завершить: ядро отвечает RST, `connect()` мгновенно возвращает ошибку `ECONNREFUSED` («Connection refused», проверено выше). Ошибка возникает **до** отправки данных.

**3. udpclient → незапущенному UDP-серверу?**
UDP не устанавливает соединений: `sendto()` успешно уходит (сообщение потеряется на хосте — порт никто не слушает, хост может ответить ICMP Port Unreachable, но это не гарантировано). Клиент блокируется в `recvfrom()`, ответа нет — **зависание** (проверено: процесс убит внешним `timeout`). Без установленного таймаута (`SO_RCVTIMEO`) или повторных попыток приложение просто ждёт вечно.

**4. tcpclient «отвалился» во время работы с сервером?**
TCP уведомляет сервер: `read()` вернёт 0 (корректный FIN при закрытии) или −1/ECONNRESET (обрыв/RST). Сервер выйдет из внутреннего цикла, закроет сокет клиента (`close(cfd)`) и продолжит принимать новые соединения в `accept()`. Данные не теряются — транспорт гарантирует доставку того, что попало в буфер до обрыва.

**5. udpclient отвалился во время работы с сервером?**
Ничего заметного: у UDP нет состояния соединения. Сервер просто перестанет получать датаграммы и будет висеть в блокирующем `recvfrom()` до следующего пакета от любого клиента. Ни ошибок, ни событий об «обрыве».

**6. udpclient → несуществующий/выключенный сервер?**
Как и в п.3: отправка «удаётся» (или через время даёт ICMP-ошибку, которую неconnected-сокет обычно не показывает), клиент зависает в `recvfrom()` без ответа. Именно поэтому UDP называют ненадёжным протоколом: доставка не гарантирована и об отсутствии доставки не сообщается.

**7. tcpclient → несуществующий/выключенный сервер?**
SYN-пакеты не получают ответа: `connect()` либо быстро падает с ECONNREFUSED (хост жив, порт закрыт), либо висит до таймаута установления соединения (~несколько минут по умолчанию, «Connection timed out») если хост недоступен полностью.

**8. Отличия UDP и TCP?**
| Признак | TCP | UDP |
|---|---|---|
| Модель | соединение (three-way handshake) | дейтаграммы без соединения |
| Надёжность | гарантия доставки, порядок, ACK/ретрансляции | best-effort, возможны потери/дубли/перестановки |
| Потоковость | байтовый поток с границами, управляемыми приложением | границы сообщений сохраняются |
| Контроль перегрузки/окно | есть (slow start, congestion control) | нет |
| Головная часть | 20+ байт | 8 байт |
| Команды API | connect/listen/accept/send/recv | sendto/recvfrom |
| Применение | файлы, HTTP, наши лабы 6–7 эхо | DNS, видеостриминг, игры, где лучше потеря, чем задержка |

## Вывод
На двух минимальных приложениях прочувствована разница между надёжным ориентированным на соединение транспортом (TCP) и ненадёжным датаграммным (UDP): поведение при отсутствующемpeer и при обрыве принципиально разное, что видно даже по коду — TCP требует accept/connect-состояния, UDP лишь чередует sendto/recvfrom.
