## Как реализовано

### Задание 1 — mutex.c с условной компиляцией
Критическая секция обёрнута в `#if USE_MUTEX ... #endif`:
```c
void *Incrementer(void *args) {
    for (int i = 0; i < N; i++) {
#if USE_MUTEX
        pthread_mutex_lock(&mutex);
#endif
        amount += delta;            // операция read-modify-write НЕ атомарна
#if USE_MUTEX
        pthread_mutex_unlock(&mutex);
#endif
    }
}
```
Сборка двух бинарников из одного исходника:
```bash
gcc -o mutex_no_lock   mutex.c -DUSE_MUTEX=0 -lpthread
gcc -o mutex_with_lock mutex.c -DUSE_MUTEX=1 -lpthread
```
**Результат:** без мьютекса итог ≠ 100 (потери инкрементов: `amount++` — это загрузка, сложение и сохранение, и два потока могут выполнить их перемешанно); с мьютексом стабильно 100. Это классическая **гонка данных** (data race).

### Задание 2 — parallel_factorial.c
- разбор `-k 10 --pnum=4 --mod=1000000007`;
- произведение `[1..k] % mod` режется между потоками: поток i считает кусок `[begin_i, end_i]` функцией `MultModulo` (безопасное умножение по модулю через «русское peasant-умножение» — без переполнения uint64);
- частичные произведения объединяются главным потоком после `pthread_join`.

**Проверка против Python (`math.factorial`):**
- `13! % 1e9+7 = 227020758` ✔
- `40! % 998244353 = 504900914` ✔

### Задание 3 — deadlock.c
Два потока захватывают два мьютекса A и B, но в **разном порядке**:
```
Thread1: lock(A) -> (sleep) -> lock(B)
Thread2: lock(B) -> (sleep) -> lock(A)
```
Каждый держит один мьютекс и ждёт другой, который навсегда занят партнёром → круг ожидания. Проверено: вывод «thread1 waiting for B… / thread2 waiting for A…» и зависание процесса (завершён внешним `timeout`, exit code 124).

Четыре условия Коффмана для взаимоблокировки: взаимное исключение, удержание-и-ожидание, отсутствие вытеснения, круг ожидания. Лечится нарушением любого из них — на практике чаще всего **единым глобальным порядком захвата блокировок** (оба потока берут сначала A, потом B).
