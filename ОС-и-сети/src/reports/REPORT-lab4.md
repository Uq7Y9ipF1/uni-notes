## Что нужно знать

### Архитектурный уровень
- **Жизненный цикл процесса:** после завершения кода ядро хранит запись с exit-статусом, пока родитель не заберёт её через `wait()`. Пока не забрал — состояние `Z` (зомби): память/CPU не держит, но занимает слот таблицы процессов (лимит `pid_max`/ulimit). Устранение: дождаться, `signal(SIGCHLD, SIG_IGN)`, или двойной fork (сироту удочеряет init/systemd и дожидается сам).
- **Неблокирующее ожидание с таймером:** вместо зависания в `wait()` — цикл `waitpid(pid, &st, WNOHANG)` (0 = ещё жив) + собственный миллисекундный таймер по `gettimeofday`; просрочка → `kill(pid, SIGKILL)` (неперехватываемый сигнал), затем того же ребёнка всё равно дождаться `waitpid` — иначе сами получим зомби. Классический паттерн «deadline-менеджмент» пула воркеров.
- **Сигналы** — асинхронные уведомления ядра→процесс; `SIGTERM` можно проигнорировать/поймать обработчиком, `SIGKILL/SIGSTOP` — нельзя никогда.
- **Виртуальное адресное пространство процесса** делится на сегменты (символы линкера): `text` (код, read-only, общий между экземплярами) до `etext`; `.data` (инициализированные глобальные) до `edata`; `.bss` (нулевые глобальные, выделяется лениво) до `end`; дальше — куча (растёт вверх через `brk/mmap`), стеки потоков, карты mmap, стек.
- **Процесс vs поток:** потоки внутри одного процесса делят адресное пространство (общие данные — плюс к скорости, минус — гонки) и имеют отдельные стеки и регистровые контексты. Переключение потока дешевле переключения процесса (нет смены page tables/TLB flush).
- **Модель pthread для суммы:** разбить массив на N диапазонов, каждому свой `pthread_create` со структурой-аргументом `{begin,end,array}`; частичные суммы складываются (ассоциативная операция) — синхронизация нужна только на завершении (`pthread_join`). Генерацию данных выносим за таймер, чтобы мерить именно распараллеливание.
- **Вынос функции в библиотеку** — та же механика, что в лабе 2: `sum.c/sum.h` → `gcc -c` → `ar rcs libsum.a` → линковка `-L. -lsum`.

### Прикладной уровень
- Ключ `--timeout` добавляется в таблицу `option` getopt_long как `required_argument`.
- Состояние зомби видно командами: `ps aux | grep defunct`, `top` (строка `<defunct>`).
- Адреса сегментов печатаются через внешние символы линкера `extern char etext, edata, end;`.
- Компиляция с pthread требует `-lpthread` (или `-pthread`).

## Реализация
- `lab4/src/parallel_min_max.c` — копия лабы 3 + разбор `--timeout`; родитель собирает PID'ы детей, крутит опрос `WNOHANG`, по истечении шлёт `SIGKILL` всем живым, дожидается всех, корректно агрегирует то, что успели прислать (pipe/файлы). Без `--timeout` поведение идентично лабе 3. Позднее оптимизировано: генерация чанка выполняется уже в ребёнке (нет гигантского общего malloc, результат не зависит от pnum).
- `lab4/src/zombie.c` — родитель `fork` + `sleep(30)` без `wait`; ребёнок немедленно выходит → `ps` показывает `Z`. В комментариях все три способа лечения.
- `lab4/src/process_memory.c` — печать адресов сегментов через символы линкера `&etext/&edata/&end`; исправлены предупреждения `-Wall`: `%8X` → `%p` с приведением к `void*` (адреса 64-битные, `%X` обрезал их до 32 бит), явный `int main(void)`, прототип `showit(char *p)` вместо устаревшего K&R-стиля. Все переменные помечены комментариями, в каком сегменте лежат (текст/данные/BSS/куча/стек).
- `lab4/src/makefile` — цели `all: parallel_min_max process_memory zombie psum`, правила для `.o`, сборка `libsum.a`, линковка psum с `-lpthread`.
- `lab4/src/parallel_sum.c` + `sum.c/sum.h` → `libsum.a`: аргументы `--threads_num --seed --array_size`, структура аргумента потока, join, итоговая сумма, замер времени только параллельной фазы.

## Команды
```bash
cd lab4/src
make                 # соберёт parallel_min_max, process_memory, zombie, psum (+ libsum.a)
make clean

# Задание 1: таймаут
./parallel_min_max --seed=42 --array_size=1000000 --pnum=4               # штатно, ~3 мс
./parallel_min_max --seed=42 --array_size=1000000 --pnum=4 --timeout=5   # уложился — тот же результат
./parallel_min_max --seed=42 --array_size=200000000 --pnum=4 --timeout=1 # дети убиты по deadline, выход без зависания

# Задание 2: зомби
./zombie &                       # родитель спит 30 c
ps -o pid,stat,comm | grep Z     # видим <defunct> в состоянии Z
wait

# Задание 3: сегменты памяти
./process_memory

# Задания 5–6: потоковая сумма
./psum --threads_num=4 --seed=42 --array_size=1000000
```

## Проверка
- Таймаут: при огромном массиве и `--timeout=1..2` программа завершается за ~N секунд, зомби нет (все waitpid выполнены); обычный запуск даёт корректный min/max.
- Зомби зафиксирован через `ps` (статус `Z`) и исчезает после выхода родителя.
- Сегменты: `etext < edata < end`, адреса лежат в разумных диапазонах текста/данных.
- `psum`: сумма совпадает с последовательным эталоном (1083572212 при seed=42, n=10⁶); время растёт пропорционально размеру и падает с числом потоков. Сборка проходит чисто, без warning'ов `-Wall` (unused-переменные удалены).

## Вывод
Освоены неблокирующее ожидание с дедлайном (waitpid/WNOHANG + SIGKILL), природа и лечение зомби-процессов, карта виртуальной памяти процесса, а также первый переход от процессов к потокам: общая память, cheap context switch, вынесение кода в библиотеку и измерение ускорения.
