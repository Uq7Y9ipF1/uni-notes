# Отчёт: Лабораторная работа №7 — Эксперименты с транспортными протоколами: TCP vs UDP

## ТЗ (что нужно было сделать по сути)
Исследовать поведение TCP и UDP на реальных замерах: сравнить надёжность, упорядоченность, скорость/задержки доставки, поведение при потере соединений; сделать выводы об областях применения каждого протокола.

## Что нужно знать

### Архитектурный уровень
- **Модель OSI/стек TCP/IP:** транспортный уровень над IP добавляет порты (мультиплексирование процессов) и — опционально — гарантии. TCP = слой гарантий поверх ненадёжного IP; UDP = почти ничего, кроме портов и контрольной суммы.
- **TCP (Transmission Control Protocol):** connection-oriented, byte-stream, reliable, ordered. Механизмы: 3-way handshake (MSS, начальные seq); подтверждение ACK с **скользящим окном** (flow control, размер окна объявляет получатель); тайм-ауты и ретрансмиссия (RTO по сглаженной RTT); обнаружение потерь по 3 duplicate-ACK и fast retransmit; контроль перегрузки (slow start → congestion avoidance, AIMD; Reno/CUBIC); упорядочивание сегментов по seq-номерам; корректное закрытие (FIN/4-way) и TIME_WAIT. Следствие: лишние round-trip на установление, head-of-line задержки, но доставка «как в файле».
- **UDP (User Datagram Protocol):** connectionless, datagram-oriented, без handshakes/ACK/ретрансмиссий/упорядочивания. Границы сообщений сохраняются (один sendmsg = один датаграмм ≤ 64KB, на практике ≤ MTU≈1472 чтобы не фрагментировать). Потеря датаграмма = потеря сообщения; порядок может меняться (IP не гарантирует). Минимальные задержки и оверхед (8-байтный заголовок против 20+) — выбор там, где свежесть важнее полноты: DNS, VoIP, игры, стриминг, мультикаст/broadcast.
- **Когда что:** надёжный поток байт → TCP; низкая задержка/широковещание/собственные механизмы восстановления поверх → UDP (+QUIC как компромисс: UDP-транспорт + надёжность в userspace).

### Прикладной уровень
- Тип сокета выбирает протокол: SOCK_STREAM↔TCP, SOCK_DGRAM↔UDP. UDP-«сервер» просто recvfrom/sendto (без accept/connect); broadcast требует SO_BROADCAST.
- Инструменты наблюдения: `ss -ti` (RTT, cwnd, retrans), `netstat -su` (UDP in/errors), `ping` (базовая RTT), `iperf3 -s/-c [-u -b]` (throughput/loss), `tcpdump/wireshark` (handshakes, dupACK, потери).
- Эмуляция потерь/задержек: `tc qdisc netem loss 10% delay 50ms` на loopback.

## Реализация (эксперименты)
Проведены натурные промеры (написанные ранее утилиты лабы 6 + стандартные инструменты):
1. **Надёжность:** передача данных через TCP-канал с обрывом соединения посередине — получатель либо дочитывает всё в порядке, либо получает явную ошибку; аналог UDP-датаграмм при `netem loss 10%` — ~10% сообщений молча исчезают, без уведомления отправителя.
2. **Упорядочение:** TCP-поток приходит строго последовательным байтовым потоком; UDP-датаграммы при нагрузке наблюдались в перемешанном порядке.
3. **Задержка первого байта:** TCP требует handshake (1 RTT, TLS ещё больше) перед данными; UDP шлёт сразу — замер round-trip «запрос-ответ»: UDP быстрее на величину handshake-обмена.
4. **Пропускная способность:** iperf3 TCP показал устойчивый выход к максимуму канала с ростом окна; UDP на фиксированном бите выше порога терял пакеты (counters в `netstat -su`).
5. **Вещание:** UDP-broadcast доставлен всем хостам подсети одним вызовом; TCP так не умеет (N соединений).

## Команды
```bash
# базовые клиенты/серверы из лабы (TCP echo / наш server-client):
cd ../lab6/src && make
./server --port=20001 --tnum=4 & ./client --file=servers.txt 13 1000000007

# наблюдение состояния TCP:
ss -ti dst 127.0.0.1            # rtt, retrans, cwnd
watch -n1 'netstat -su | grep -E "InDatagrams|receive errors"'

# эмуляция плохой сети (нужен root):
sudo tc qdisc add dev lo root netem loss 10% delay 50ms
...повторить эксперименты...
sudo tc qdisc del dev lo root

# замеры throughput:
iperf3 -s                          # на одной машине
iperf3 -c 127.0.0.1                # TCP
iperf3 -c 127.0.0.1 -u -b 100M     # UDP, битрейт 100 Мбит, смотрим lost%%
```

## Результаты и вывод
Эксперименты подтвердили теорию: TCP обеспечивает гарантированную упорядоченную доставку ценой handshake, ACK-оверхеда и возможного роста задержки при потерях (ретрансмиссии блокируют поток — HOL); UDP даёт минимальную задержку и поддерживает broadcast, но теряет данные молча и не следит за порядком. Рекомендация: для прикладных задач курса (расчёт по запросу) — TCP; для телеметрии/медиа — UDP с собственным протоколом целостности поверх.
