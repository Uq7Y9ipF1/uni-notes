# Отчёт: Лабораторная работа №5 — Синхронизация потоков: мьютексы, гонки, взаимоблокировки

## ТЗ (что нужно было сделать по сути)
1. В программе `mutex.c` демонстрацию data race собрать в двух вариантах одной программой (`-DUSE_MUTEX=0/1`): без мьютекса счётчик «теряет» инкременты, с мьютексом — корректные 100.
2. Параллельное вычисление факториала по модулю: `parallel_factorial.c` (`-k --pnum --mod`) — диапазон множителей делится между потоками, объединение под мьютексом, умножение по модулю.
3. Создать **взаимоблокировку (deadlock)** двумя потоками на двух мьютексах и объяснить условия его возникновения.

## Что нужно знать

### Архитектурный уровень
- **Data race:** операция `counter++` — это read-modify-write (load, add, store). Два потока на одном ядре/с разными кэшами могут выполнить load одного старого значения и оба записать `old+1` — один инкремент теряется. Компилятор/CPU дополнительно разрешают переупорядочивания. Итог: результат недетерминирован и обычно меньше ожидаемого.
- **Мьютекс** — примитив блокировки на уровне ядра: `pthread_mutex_lock` гарантирует, что критическая секция исполняется одним потоком; остальные засыпают в очереди ожидания (futex), а не крутятся — экономия CPU против spinlock при длинных секциях. Стоимость — переходы user↔kernel, поэтому держать лок надо минимальным куском кода.
- **Атомарность vs целостность:** даже если бы `++` был атомарен, сложные инварианты всё равно требуют лок; но для суммы частичных результатов достаточно сложения под мьютексом или атомарных операций.
- **Четыре условия deadlock (коффман):** взаимное исключение, удержание и ожидание, отсутствие вытеснения, **циклическое ожидание**. Классический пример: поток 1 берёт A→B, поток 2 берёт B→A. Лечится тотально — **строгим порядком захвата ресурсов** (все берут сначала A, потом B), либо trylock+откат, либо таймаутами.
- **Распределение работы в factorial:** произведение ассоциативно/коммутативно → `(a*b mod m)` можно считать частями: каждый поток считает произведение своего диапазона `[begin,end)`, затем результаты сливаются. Умножение по модулю требует аккуратности к переполнению 64-бит (используется MultModulo из лабы 6-common).

### Прикладной уровень
- Сборка вариантов одной командой через `-D`: `gcc -DUSE_MUTEX=0 ...` / `-DUSE_MUTEX=1 ...`.
- Проверка гонок статистически: несколько прогонов, разные `--pnum`.
- Диагноз зависания: `ps` (процесс жив, CPU ~0), `gdb -p PID` + `thread apply all bt` видно две блокировки в pthread_mutex_lock.

## Реализация
- `lab5/src/mutex.c` — общий код: N потоков инкрементируют глобальный счётчик; критическая секция оборачивается `#if USE_MUTEX` вокруг lock/unlock. Две сборки дают два поведения.
- `lab5/src/parallel_factorial.c` — getopt_long `-k/-pnum/--mod`; структура аргумента потока `{begin,end,mod}`; каждый поток возвращает произведение своего отрезка; родитель под мьютексом домножает общий результат; вывод `k! % mod`.
- `lab5/src/deadlock.c` — два мьютекса m1,m2; поток 1: lock(m1)→sleep→lock(m2); поток 2: lock(m2)→sleep→lock(m1). Потоки гарантированно обмениваются ролями по времени сна и зависают; печать маркеров «waiting for…».
- `lab5/src/makefile` — цели mutex_nomutex, mutex_ok, parallel_factorial, deadlock.

## Команды
```bash
cd lab5/src
make

# Задание 1: гонка vs мьютекс
gcc -DUSE_MUTEX=0 mutex.c -o mutex_race -lpthread
gcc -DUSE_MUTEX=1 mutex.c -o mutex_safe -lpthread
./mutex_race     # например: counter = 78 (меньше 100, нестабильно)
./mutex_safe     # всегда counter = 100

# Задание 2: параллельный факториал по модулю
./parallel_factorial -k 10 --pnum=4 --mod=1000000007   # -> 13! % ... эталон Python: 227020758 (для k=13)
./parallel_factorial -k 40 --pnum=4 --mod=998244353    # эталон: 504900914

# Задание 3: дедлок
./deadlock            # зависает после двух сообщений waiting
timeout 5 ./deadlock; echo $?   # 124 — принудительно убит по времени
```

## Проверка
- `mutex_race` при нескольких прогонах даёт разные значения < 100; `mutex_safe` стабильно 100 — мьютекс устраняет гонку.
- Результаты `parallel_factorial` сверены с Python (`math.factorial(k)%mod`) — совпадают для разных k/pnum/mod.
- `deadlock` воспроизвёл зависание (exit code 124 от `timeout`), что подтверждает циклическое ожидание.
